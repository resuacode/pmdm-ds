# Corrutinas en Kotlin

Las corrutinas son una característica de Kotlin que permite escribir código asíncrono de manera más sencilla y legible. Las corrutinas son funciones que pueden suspenderse y reanudarse en un punto determinado, lo que permite realizar operaciones asíncronas sin bloquear el hilo en el que se ejecutan.    

:::info[Dependencia necesaria]
Las corrutinas no forman parte de la librería estándar, sino de la librería `kotlinx.coroutines`. En un proyecto Android ya viene incluida a través de las librerías de Jetpack. En un proyecto Kotlin de consola hay que añadir la dependencia `org.jetbrains.kotlinx:kotlinx-coroutines-core`.

En el [Kotlin Playground](https://play.kotlinlang.org/) ya está disponible, por lo que podemos probar todos los ejemplos de esta página directamente allí.
:::

```kotlin
import kotlinx.coroutines.*

fun main() = runBlocking {
    val resultado = async { obtenerDatos() }
    println("Datos: ${resultado.await()}")
}

suspend fun obtenerDatos(): String {
    delay(1000)
    return "Datos obtenidos"
}
```

En el ejemplo anterior, se define una función `obtenerDatos` que simula una operación asíncrona que tarda 1 segundo en completarse. La función `main` utiliza `runBlocking` para crear un ámbito de corrutinas, lanza `obtenerDatos` en una corrutina con `async` y espera a su resultado con `await`. 

## Código síncrono

El código síncrono es el código que se ejecuta de manera secuencial, es decir, una instrucción se ejecuta después de que la anterior haya terminado, y mientras una operación larga está en marcha el hilo queda **bloqueado** esperando.

```kotlin
fun main() {
    val resultado = obtenerDatos()
    println("Datos: $resultado")
}

fun obtenerDatos(): String {
    Thread.sleep(1000) // Bloquea el hilo durante 1 segundo
    return "Datos obtenidos"
}
```

En el ejemplo anterior, se define una función `obtenerDatos` que simula una operación síncrona que tarda 1 segundo en completarse. La función `main` llama a la función `obtenerDatos` y el hilo no puede hacer nada más hasta que termina.

En Android esto es un problema grave: si bloqueamos el **hilo principal** (el que dibuja la interfaz), la app se congela y, si tarda demasiado, el sistema muestra el diálogo de "La aplicación no responde" (ANR).

## Código asíncrono

El código asíncrono permite que varias tareas avancen de forma concurrente: mientras una tarea espera (por ejemplo, la respuesta de un servidor), el hilo queda libre para hacer otras cosas. En Kotlin, el código asíncrono se escribe utilizando corrutinas.

```kotlin
import kotlinx.coroutines.*

fun main() = runBlocking {
    launch { tarea("A") }
    launch { tarea("B") }
    println("Tareas lanzadas")
}

suspend fun tarea(nombre: String) {
    delay(1000) // Suspende la corrutina, pero NO bloquea el hilo
    println("Tarea $nombre terminada")
}
```

Al ejecutarlo, se imprime primero "Tareas lanzadas" y, un segundo después, las dos tareas terminan casi a la vez: el programa tarda 1 segundo en total y no 2, aunque todo se ejecuta en un único hilo.

## Funciones de suspensión (`suspend`)

La palabra clave `suspend` marca una función que puede **suspenderse**: pausar su ejecución sin bloquear el hilo y reanudarla más tarde. Por ejemplo, `delay()` es una función de suspensión, mientras que `Thread.sleep()` bloquea el hilo.

Una función `suspend` solo puede llamarse desde otra función `suspend` o desde dentro de una corrutina (por ejemplo, dentro de `launch`, `async` o `runBlocking`).

## Constructores de corrutinas: `runBlocking`, `launch` y `async`

- `runBlocking`: crea una corrutina y **bloquea** el hilo actual hasta que termina. Solo se usa en funciones `main` o en tests, para conectar el código normal con el mundo de las corrutinas. **Nunca** en el código de una app Android.
- `launch`: lanza una corrutina que no devuelve ningún resultado (*fire and forget*). Devuelve un `Job` con el que podemos esperarla o cancelarla.
- `async`: lanza una corrutina que devuelve un resultado. Devuelve un `Deferred<T>`, cuyo valor obtenemos con `await()`.

```kotlin
import kotlinx.coroutines.*

fun main() = runBlocking {
    // launch: no devuelve resultado
    val job = launch {
        delay(500)
        println("Tarea en segundo plano terminada")
    }

    // async: devuelve un resultado
    val precio = async { obtenerPrecio() }
    val stock = async { obtenerStock() }
    println("Precio: ${precio.await()}, stock: ${stock.await()}")

    job.join() // Espera a que termine la corrutina lanzada con launch
}

suspend fun obtenerPrecio(): Double {
    delay(1000)
    return 19.99
}

suspend fun obtenerStock(): Int {
    delay(1000)
    return 42
}
```

En el ejemplo anterior, `obtenerPrecio` y `obtenerStock` se ejecutan en paralelo gracias a `async`, por lo que obtener ambos datos tarda 1 segundo y no 2.

:::info[`launch` y `async` son funciones de extensión de `CoroutineScope`]
`launch` y `async` solo pueden llamarse sobre un `CoroutineScope` (un ámbito de corrutinas). Dentro del bloque de `runBlocking`, `launch` o `async` ya estamos en un `CoroutineScope`, por eso podemos llamarlas directamente. En Android usaremos los ámbitos que nos proporciona el sistema, como `viewModelScope`.
:::

## Excepciones

Las excepciones lanzadas dentro de una corrutina se pueden capturar con bloques `try-catch`, igual que en el código normal:

```kotlin
import kotlinx.coroutines.*

fun main() = runBlocking {
    try {
        val datos = obtenerDatos()
        println("Datos: $datos")
    } catch (e: Exception) {
        println("Error: ${e.message}")
    }
}

suspend fun obtenerDatos(): String {
    delay(1000)
    throw Exception("Error al obtener los datos")
}
```

En el ejemplo anterior, `obtenerDatos` simula una operación que falla. Como la llamamos directamente (es una función `suspend`), el `try-catch` captura la excepción.

:::warning[Excepciones y corrutinas hijas]
Cuando una corrutina lanzada con `launch` o `async` falla, la excepción **se propaga a su corrutina padre**, que se cancela junto con el resto de sus hijas. Por eso lo más sencillo y seguro es capturar las excepciones **dentro** de la propia corrutina:

```kotlin
launch {
    try {
        obtenerDatos()
    } catch (e: Exception) {
        println("Error: ${e.message}")
    }
}
```

Para tratar de forma global las excepciones no capturadas de las corrutinas lanzadas con `launch`, se puede añadir un `CoroutineExceptionHandler` al contexto del ámbito:

```kotlin
val manejador = CoroutineExceptionHandler { _, exception ->
    println("Error no controlado: ${exception.message}")
}

val scope = CoroutineScope(SupervisorJob() + manejador)
scope.launch { obtenerDatos() } // El error lo recibe el manejador
```
:::

Más información en la [documentación oficial de Kotlin sobre excepciones en corrutinas](https://kotlinlang.org/docs/exception-handling.html).

## Cancelación

Las corrutinas se pueden cancelar llamando a `cancel()` sobre su `Job`. La cancelación es **cooperativa**: la corrutina no se detiene en cualquier punto, sino en el siguiente punto de suspensión (por ejemplo, en un `delay()`), donde se lanza una `CancellationException`.

```kotlin
import kotlinx.coroutines.*

fun main() = runBlocking {
    val job = launch {
        try {
            obtenerDatos()
        } finally {
            println("Corrutina cancelada, liberando recursos")
        }
    }
    delay(500)
    job.cancel()
    job.join()
    println("Fin")
}

suspend fun obtenerDatos() {
    delay(1000)
    println("Datos obtenidos") // Nunca llega a ejecutarse
}
```

En el ejemplo anterior, la corrutina se cancela a los 500 milisegundos, mientras está suspendida en `delay(1000)`. El bloque `finally` se ejecuta igualmente y nos permite liberar recursos.

:::warning[No captures `CancellationException`]
Si capturamos `Exception` de forma genérica dentro de una corrutina, también estaremos capturando la `CancellationException`, y la corrutina podría seguir ejecutándose aunque se haya cancelado. Si necesitamos un `catch (e: Exception)`, conviene volver a lanzar las excepciones de cancelación.
:::

## La clase Job

Un `Job` representa una corrutina en ejecución: permite consultar su estado (`isActive`, `isCompleted`, `isCancelled`), esperar a que termine con `join()` o cancelarla con `cancel()`. `launch` devuelve un `Job`, y `async` devuelve un `Deferred`, que es un tipo de `Job` con resultado.

:::info[La importancia de Job]
Job desempeña un papel importante para garantizar la **concurrencia estructurada**, ya que administra el ciclo de vida de las corrutinas y mantiene la relación entre corrutinas padre e hijas.
:::

### Jerarquía de trabajos

Cuando lanzamos una corrutina dentro de otra, la nueva corrutina es **hija** de la primera. Esta jerarquía tiene varias consecuencias:

- Una corrutina padre no termina hasta que terminan todas sus hijas.
- Si se cancela la corrutina padre, se cancelan todas sus hijas.
- Si una hija falla con una excepción, se cancela el padre y, con él, el resto de hijas.

```kotlin
import kotlinx.coroutines.*

fun main() = runBlocking {
    val padre = launch {
        launch {
            delay(1000)
            println("Hija 1 terminada") // No se imprime
        }
        launch {
            delay(1000)
            println("Hija 2 terminada") // No se imprime
        }
    }

    delay(500)
    padre.cancel() // Cancela también las dos corrutinas hijas
    padre.join()
    println("Padre e hijas canceladas")
}
```

## CoroutineScope

Un `CoroutineScope` es un ámbito que agrupa corrutinas y controla su ciclo de vida: cuando se cancela el ámbito, se cancelan todas las corrutinas lanzadas en él. Esto evita dejar corrutinas "huérfanas" trabajando cuando ya no hacen falta.

En Android casi nunca crearemos nuestros propios ámbitos, sino que usaremos los que proporciona Jetpack:

- `viewModelScope`: ligado a un `ViewModel`. Se cancela cuando el ViewModel se destruye.
- `lifecycleScope`: ligado al ciclo de vida de una `Activity` o `Fragment`.
- `rememberCoroutineScope()` y `LaunchedEffect`: ligados a un composable. Se cancelan cuando el composable sale de la pantalla.

Aun así, podemos crear un ámbito propio a partir de un contexto:

```kotlin
import kotlinx.coroutines.*

fun main() = runBlocking {
    val scope = CoroutineScope(Dispatchers.Default + SupervisorJob())

    scope.launch {
        obtenerDatos()
    }

    delay(500)
    scope.cancel() // Cancela todas las corrutinas del ámbito
    println("Ámbito cancelado")
}

suspend fun obtenerDatos() {
    delay(1000)
    println("Datos obtenidos") // No se imprime
}
```

Si lo que queremos es lanzar varias corrutinas desde una función `suspend` y esperar a que terminen todas, usamos la función `coroutineScope { }`:

```kotlin
suspend fun cargarTodo() = coroutineScope {
    val usuarios = async { obtenerUsuarios() }
    val productos = async { obtenerProductos() }
    Pair(usuarios.await(), productos.await())
}
```

## CoroutineContext

Toda corrutina se ejecuta dentro de un `CoroutineContext`, que es en esencia un conjunto de elementos que definen cómo se ejecuta. Los más comunes son:

- `Job`: controla el ciclo de vida de la corrutina.
- `CoroutineDispatcher`: define en qué hilo o grupo de hilos se ejecuta la corrutina. 
- `CoroutineName`: un nombre para la corrutina, útil para depurar.
- `CoroutineExceptionHandler`: maneja las excepciones no capturadas.

Los elementos del contexto se combinan con el operador `+`:

```kotlin
import kotlinx.coroutines.*

fun main() = runBlocking {
    launch(Dispatchers.Default + CoroutineName("MiCorrutina")) {
        println("Ejecutándose en ${Thread.currentThread().name}")
    }
}
```

## CoroutineDispatcher

El `CoroutineDispatcher` define en qué hilo o grupo de hilos se ejecuta una corrutina. Los despachadores predefinidos son:

- `Dispatchers.Main`: el hilo principal de Android (el de la UI). Es el que usan por defecto `viewModelScope` y los efectos de Compose. Solo existe en plataformas con hilo de UI, por lo que no está disponible en un `main` de consola.
- `Dispatchers.IO`: optimizado para operaciones de entrada/salida que pasan mucho tiempo esperando (red, ficheros, bases de datos).
- `Dispatchers.Default`: optimizado para tareas que usan mucha CPU (cálculos, ordenar listas grandes, procesar JSON...).

Para cambiar de dispatcher dentro de una corrutina se usa `withContext`, que ejecuta el bloque en el dispatcher indicado y devuelve su resultado:

```kotlin
import kotlinx.coroutines.*

fun main() = runBlocking {
    val contenido = leerFichero()
    println(contenido)
}

suspend fun leerFichero(): String = withContext(Dispatchers.IO) {
    // Aquí haríamos la lectura real del fichero
    delay(1000)
    "Contenido del fichero"
}
```

En el ejemplo anterior, `leerFichero` cambia al dispatcher `IO` para hacer el trabajo y el resultado vuelve automáticamente a quien la llamó.

:::tip[Funciones seguras para el hilo principal]
Una buena práctica en Android es que las funciones `suspend` de la capa de datos usen `withContext` internamente, de forma que se puedan llamar desde cualquier hilo (incluido el principal) sin preocuparnos. Librerías como Retrofit o Room ya lo hacen por nosotros en sus funciones `suspend`.
:::
