# Gestión de estado en Jetpack Compose

Con Compose definimos la interfaz de usuario de manera declarativa: describimos cómo se ve la pantalla **en función del estado** de la aplicación, y cuando el estado cambia, Compose vuelve a dibujar automáticamente las partes afectadas.

## Estado en Jetpack Compose

El estado representa cualquier información que puede cambiar a lo largo del tiempo y que afecta a la apariencia o al comportamiento de la interfaz: el valor de un contador, el texto escrito en un campo, la lista de elementos que se muestra, si un diálogo está abierto o no...

Cuando un composable **lee** un estado y ese estado cambia, Compose vuelve a ejecutar ese composable para actualizar la pantalla. Este proceso se llama **recomposición**.

## Definición de estado con `mutableStateOf`

Para que Compose sepa que un valor es un estado y pueda "observarlo", se crea con la función `mutableStateOf()`, que devuelve un objeto `MutableState<T>` con una propiedad `value`.

```kotlin
val contador = mutableStateOf(0)
```

En el ejemplo anterior, se define un estado `contador` con un valor inicial de `0`. Para leerlo o modificarlo se usa su propiedad `value`:

```kotlin
println(contador.value) // Lee el estado
contador.value++        // Modifica el estado y provoca una recomposición
```

No hace falta llamar a ninguna función para "observar" el estado: basta con que un composable lea `contador.value` para que Compose lo tenga en cuenta.

## Uso de `remember`

Cada recomposición vuelve a ejecutar la función composable desde el principio. Si creamos el estado directamente dentro del composable, en cada recomposición se crearía un estado nuevo con el valor inicial y el contador nunca pasaría de 0. Para evitarlo, usamos `remember`, que guarda el objeto entre recomposiciones:

```kotlin
@Composable
fun Contador() {
    val contador = remember { mutableStateOf(0) }

    Button(onClick = { contador.value++ }) {
        Text(text = "Contador: ${contador.value}")
    }
}
```

En el ejemplo anterior, se utiliza la función `remember` para que el estado `contador` se conserve entre recomposiciones. Al hacer clic en el botón, se incrementa el valor, Compose detecta el cambio y vuelve a dibujar el texto.

:::danger[¡Importante!]
Un `mutableStateOf` creado dentro de un composable **siempre** debe ir envuelto en `remember` (o `rememberSaveable`). Android Studio muestra un error si lo olvidamos.
:::

### Delegación con `by`

Escribir `.value` continuamente resulta pesado. Con la palabra clave `by` podemos delegar la propiedad en el estado y trabajar con ella como si fuera una variable normal:

```kotlin
import androidx.compose.runtime.getValue
import androidx.compose.runtime.setValue

@Composable
fun Contador() {
    var contador by remember { mutableStateOf(0) }

    Button(onClick = { contador++ }) {
        Text(text = "Contador: $contador")
    }
}
```

Fíjate en que ahora la variable se declara con `var` y en los dos `import`, necesarios para que funcione la delegación (Android Studio los añade automáticamente con `Alt + Enter`). Esta es la forma más habitual de declarar estado en un composable.

:::tip[Estados de tipos primitivos]
Para números existen versiones optimizadas que evitan convertir el valor en un objeto: `mutableIntStateOf(0)`, `mutableFloatStateOf(0f)`, `mutableLongStateOf(0L)` y `mutableDoubleStateOf(0.0)`. Android Studio sugiere usarlas cuando escribimos `mutableStateOf(0)`.
:::

## Uso de `rememberSaveable`

`remember` conserva el estado entre recomposiciones, pero **no** cuando la actividad se destruye y se vuelve a crear, cosa que ocurre, por ejemplo, al girar la pantalla o al cambiar de modo claro a oscuro. Para esos casos está `rememberSaveable`:

```kotlin
@Composable
fun Contador() {
    var contador by rememberSaveable { mutableIntStateOf(0) }

    Button(onClick = { contador++ }) {
        Text(text = "Contador: $contador")
    }
}
```

:::tip[remember vs rememberSaveable]
La diferencia entre `remember` y `rememberSaveable` es que `rememberSaveable` guarda el estado en el `Bundle` de la actividad para que se pueda restaurar después de una recreación de la actividad.

Solo puede guardar tipos que quepan en un `Bundle` (números, `String`, `Boolean`, clases `@Parcelize`...). Para estado más complejo o que debe sobrevivir más tiempo, usaremos un **ViewModel**.
:::

## Uso de `derivedStateOf`

La función `derivedStateOf` crea un estado que se calcula a partir de otros estados. Es útil cuando el estado de origen cambia muy a menudo pero el resultado cambia pocas veces, ya que así evitamos recomposiciones innecesarias.

```kotlin
@Composable
fun ListaConBotonSubir(listState: LazyListState) {
    val mostrarBotonSubir by remember {
        derivedStateOf { listState.firstVisibleItemIndex > 0 }
    }

    if (mostrarBotonSubir) {
        Button(onClick = { /* Volver arriba */ }) { Text("Subir") }
    }
}
```

En el ejemplo anterior, la posición de la lista cambia continuamente mientras el usuario se desplaza, pero `mostrarBotonSubir` solo cambia (y provoca una recomposición) cuando pasa de `true` a `false` o viceversa.

Para cálculos sencillos no hace falta `derivedStateOf`: basta con calcular el valor directamente en el composable (`val doble = contador * 2`).

## Listas como estado

Si guardamos una `MutableList` normal en un `mutableStateOf`, Compose **no** detecta que se añaden o eliminan elementos, porque la lista sigue siendo el mismo objeto. Tenemos dos opciones:

```kotlin
// Opción 1: una lista observable por Compose
val tareas = remember { mutableStateListOf<String>() }
tareas.add("Nueva tarea") // Provoca recomposición

// Opción 2: una lista de solo lectura que sustituimos por otra nueva
var tareas by remember { mutableStateOf(listOf<String>()) }
tareas = tareas + "Nueva tarea" // Nueva lista: provoca recomposición
```

La segunda opción es la que usaremos con los ViewModel, ya que trabajar con datos inmutables hace que el estado sea más predecible.

## Elevación del estado (*state hoisting*)

Un composable que guarda su propio estado es cómodo, pero difícil de reutilizar y de probar, porque nadie desde fuera puede leer ni modificar ese estado. La **elevación del estado** consiste en sacar el estado del composable y sustituirlo por dos parámetros:

- `valor: T`: el valor actual que debe mostrar.
- `onValorChange: (T) -> Unit`: una función (lambda) a la que llama cuando se produce un evento que debería cambiar el valor.

```kotlin
@Composable
fun PantallaContador() {
    var contador by rememberSaveable { mutableIntStateOf(0) }

    Column {
        ContadorTexto(contador = contador)
        ContadorBoton(onIncrementar = { contador++ })
    }
}

@Composable
fun ContadorTexto(contador: Int, modifier: Modifier = Modifier) {
    Text(text = "Contador: $contador", modifier = modifier)
}

@Composable
fun ContadorBoton(onIncrementar: () -> Unit, modifier: Modifier = Modifier) {
    Button(onClick = onIncrementar, modifier = modifier) {
        Text(text = "Incrementar")
    }
}
```

En el ejemplo anterior, el estado vive en `PantallaContador` y se comparte con sus hijos. `ContadorTexto` y `ContadorBoton` no tienen estado propio (son *stateless*): reciben el dato que tienen que mostrar y avisan de los eventos mediante lambdas.

Este patrón se conoce como **flujo unidireccional de datos** (*Unidirectional Data Flow*, UDF): **el estado baja** del padre a los hijos como parámetros y **los eventos suben** de los hijos al padre como llamadas a lambdas.

Es exactamente el mismo patrón que usan los componentes de Material, como `TextField(value = texto, onValueChange = { texto = it })`.

:::warning[No pases `MutableState` a los hijos]
Aunque es posible pasar un `MutableState<Int>` a un composable hijo para que lo modifique directamente, no es una buena práctica: el hijo puede cambiar el estado de cualquier forma y se pierde el control de quién lo modifica. Es preferible pasar el valor y una lambda.
:::

## Flows en Kotlin

Cuando el estado no vive en la interfaz sino en capas inferiores (un ViewModel, una base de datos...), no se usa `mutableStateOf`, sino **Flows**.

Un `Flow` es una secuencia de valores que se emiten de forma asíncrona a lo largo del tiempo. Por ejemplo, Room puede devolver un `Flow<List<Usuario>>` que emite una nueva lista cada vez que cambia la tabla.

```kotlin
val numeros: Flow<Int> = flow {
    for (i in 1..5) {
        delay(1000)
        emit(i) // Emite un valor cada segundo
    }
}
```

Un `Flow` no hace nada hasta que alguien lo recoge con `collect()`, que es una función `suspend` y por tanto debe llamarse desde una corrutina:

```kotlin
numeros.collect { numero ->
    println(numero)
}
```

Los flows se pueden transformar con operadores similares a los de las colecciones, como `map` o `filter`:

```kotlin
val cuadrados = numeros.map { numero -> numero * numero }
val pares = numeros.filter { numero -> numero % 2 == 0 }
```

### StateFlow

Un `StateFlow` es un tipo especial de flow que **siempre tiene un valor actual** y emite cada nuevo valor a quien lo esté observando. Es la forma recomendada de exponer el estado de la interfaz desde un ViewModel:

```kotlin
data class ContadorUiState(val contador: Int = 0)

class ContadorViewModel : ViewModel() {
    private val _uiState = MutableStateFlow(ContadorUiState())
    val uiState: StateFlow<ContadorUiState> = _uiState.asStateFlow()

    fun incrementar() {
        _uiState.update { it.copy(contador = it.contador + 1) }
    }
}
```

La versión mutable (`_uiState`) es privada para que solo el ViewModel pueda modificarla, y hacia fuera se expone una versión de solo lectura (`uiState`). La función `update` modifica el valor de forma segura aunque se llame desde varios hilos a la vez.

## Flows en Jetpack Compose

Para usar un flow en un composable, lo convertimos en un estado de Compose con `collectAsStateWithLifecycle()`:

```kotlin
@Composable
fun PantallaContador(viewModel: ContadorViewModel = viewModel()) {
    val uiState by viewModel.uiState.collectAsStateWithLifecycle()

    Column {
        ContadorTexto(contador = uiState.contador)
        ContadorBoton(onIncrementar = viewModel::incrementar)
    }
}
```

`collectAsStateWithLifecycle()` recoge el flow mientras la app está visible y deja de hacerlo cuando pasa a segundo plano, ahorrando recursos. Requiere la dependencia `androidx.lifecycle:lifecycle-runtime-compose`. La función `viewModel()` requiere `androidx.lifecycle:lifecycle-viewmodel-compose`.

Si el flow no es un `StateFlow` (no tiene valor actual), hay que indicar un valor inicial: `flow.collectAsStateWithLifecycle(initialValue = emptyList())`.

:::info[`collectAsState` vs `collectAsStateWithLifecycle`]
También existe `collectAsState()`, que funciona igual pero sigue recogiendo el flow aunque la app esté en segundo plano. En Android se recomienda `collectAsStateWithLifecycle()`.
:::

## Conclusión

- El estado de la interfaz se guarda con `mutableStateOf` envuelto en `remember` o `rememberSaveable`, y se suele declarar con `by`.
- Los composables deberían ser, siempre que se pueda, *stateless*: reciben el estado como parámetros y notifican los eventos mediante lambdas.
- Cuando el estado forma parte de la lógica de la pantalla, se eleva hasta un **ViewModel**, que lo expone como un `StateFlow` que la interfaz recoge con `collectAsStateWithLifecycle()`.
