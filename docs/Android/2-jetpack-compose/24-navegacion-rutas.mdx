# Navegación y rutas en Jetpack Compose

La mayoría de apps tienen varias pantallas. En Jetpack Compose, la navegación entre ellas se gestiona con la librería **Navigation Compose**, que se encarga de mostrar la pantalla correspondiente a cada ruta, de mantener la pila de pantallas (*back stack*) y de gestionar el botón "atrás" del sistema.

## Configuración de la navegación

Para usar Navigation Compose necesitamos añadir su dependencia. Además, como definiremos las rutas como clases serializables, necesitamos el plugin y la librería de `kotlinx.serialization`.

En el archivo `gradle/libs.versions.toml`:

```toml title="libs.versions.toml"
[versions]
navigationCompose = "2.10.2"
kotlinxSerialization = "1.11.0"

[libraries]
androidx-navigation-compose = { group = "androidx.navigation", name = "navigation-compose", version.ref = "navigationCompose" }
kotlinx-serialization-json = { group = "org.jetbrains.kotlinx", name = "kotlinx-serialization-json", version.ref = "kotlinxSerialization" }

[plugins]
# La versión debe coincidir con la versión de Kotlin del proyecto
kotlin-serialization = { id = "org.jetbrains.kotlin.plugin.serialization", version.ref = "kotlin" }
```

Y en el `build.gradle.kts` del módulo `app`:

```kotlin title="app/build.gradle.kts"
plugins {
    // ...
    alias(libs.plugins.kotlin.serialization)
}

dependencies {
    implementation(libs.androidx.navigation.compose)
    implementation(libs.kotlinx.serialization.json)
}
```

:::warning[Sobre las versiones]
Las versiones indicadas son las estables en el momento de escribir estos apuntes. Android Studio avisa (subrayando la versión) cuando hay una más reciente disponible.
:::

## Elementos principales

- **Ruta**: identifica a cada pantalla. Desde Navigation 2.8 se definen como objetos o clases anotadas con `@Serializable`, lo que se conoce como **navegación con seguridad de tipos** (*type-safe navigation*): si nos equivocamos en el nombre de una ruta o en el tipo de un argumento, el código no compila.
- **`NavController`**: el objeto que controla la navegación. Se crea con `rememberNavController()` y es el que usamos para navegar (`navigate`) o volver atrás (`popBackStack`).
- **`NavHost`**: el composable que muestra la pantalla correspondiente a la ruta actual. Dentro de él se define el **grafo de navegación**, es decir, qué composable se muestra para cada ruta.

## Definición de rutas

Las rutas sin argumentos se definen como `object` y las rutas con argumentos como `data class`:

```kotlin
import kotlinx.serialization.Serializable

@Serializable
object Inicio

@Serializable
object Perfil

@Serializable
data class Detalle(val id: Int)
```

:::tip[Organizar las rutas]
Es habitual agrupar todas las rutas en un mismo archivo (por ejemplo, `navigation/Rutas.kt`). También se pueden agrupar dentro de una interfaz sellada para tenerlas localizadas:

```kotlin
sealed interface Ruta {
    @Serializable data object Inicio : Ruta
    @Serializable data object Perfil : Ruta
    @Serializable data class Detalle(val id: Int) : Ruta
}
```
:::

## Navegación en Jetpack Compose

Con las rutas definidas, creamos el `NavHost`, indicando el `NavController`, la ruta inicial (`startDestination`) y un `composable<Ruta>` para cada pantalla:

```kotlin
@Composable
fun MyApp() {
    val navController = rememberNavController()

    NavHost(navController = navController, startDestination = Inicio) {
        composable<Inicio> {
            PantallaInicio()
        }
        composable<Perfil> {
            PantallaPerfil()
        }
    }
}
```

En el ejemplo anterior, se define un componente `MyApp` que utiliza `NavHost` para implementar la navegación entre dos pantallas: `PantallaInicio` y `PantallaPerfil`. Normalmente, `MyApp` es el composable que se llama desde `setContent` en la `MainActivity`.

## Navegación entre pantallas

Para ir a otra pantalla se llama a `navigate` pasándole la ruta de destino. La nueva pantalla se añade a la pila, y al pulsar "atrás" se vuelve a la anterior:

```kotlin
navController.navigate(Perfil)
```

Para volver atrás desde código (por ejemplo, desde la flecha de una barra superior):

```kotlin
navController.popBackStack()
```

### Opciones de navegación

La función `navigate` acepta un bloque de opciones para controlar cómo se modifica la pila de pantallas:

```kotlin
navController.navigate(Inicio) {
    // Elimina de la pila todas las pantallas hasta Inicio (incluida)
    popUpTo<Inicio> { inclusive = true }
    // Evita apilar dos veces la misma pantalla si ya está arriba del todo
    launchSingleTop = true
}
```

Esto es útil, por ejemplo, para que tras un login el usuario no pueda volver a la pantalla de login con el botón "atrás", o para volver a la pantalla principal borrando todas las intermedias.

## Navegación entre pantallas usando lambdas

Podríamos pasar el `navController` a cada pantalla para que navegue ella misma, pero no es una buena práctica: las pantallas quedarían acopladas a la navegación y serían difíciles de reutilizar y de previsualizar.

Lo recomendable es que cada pantalla reciba **lambdas** para los eventos de navegación (igual que con la [elevación del estado](./22-state-management.mdx#elevación-del-estado-state-hoisting)), y que sea el `NavHost` quien decida a dónde se navega:

```kotlin
NavHost(navController = navController, startDestination = Inicio) {
    composable<Inicio> {
        PantallaInicio(
            onIrAPerfil = { navController.navigate(Perfil) }
        )
    }
    composable<Perfil> {
        PantallaPerfil(
            onVolver = { navController.popBackStack() }
        )
    }
}
```

```kotlin
@Composable
fun PantallaInicio(onIrAPerfil: () -> Unit) {
    Button(onClick = onIrAPerfil) {
        Text(text = "Ir al perfil")
    }
}

@Composable
fun PantallaPerfil(onVolver: () -> Unit) {
    Button(onClick = onVolver) {
        Text(text = "Volver")
    }
}
```

De esta forma, toda la lógica de navegación queda en un único sitio y las pantallas no saben nada de ella.

## Paso de datos entre pantallas

Para pasar datos a una pantalla, los incluimos como propiedades de su ruta. Al navegar, creamos una instancia de la ruta con los valores:

```kotlin
@Serializable
data class Detalle(val id: Int, val titulo: String? = null)

// Navegar pasando argumentos
navController.navigate(Detalle(id = 42, titulo = "Mi elemento"))
```

Los argumentos pueden ser de tipos básicos (`Int`, `Long`, `Float`, `Boolean`, `String`), de sus versiones nulables o listas de ellos. Si un argumento es opcional, le damos un valor por defecto o lo hacemos nulable, como `titulo` en el ejemplo.

## Recuperación de datos en la pantalla de destino

En el `NavHost`, la lambda de `composable<Detalle>` recibe la entrada de la pila (`backStackEntry`), a partir de la cual obtenemos la ruta con sus argumentos usando `toRoute()`:

```kotlin
composable<Detalle> { backStackEntry ->
    val detalle: Detalle = backStackEntry.toRoute()
    PantallaDetalle(id = detalle.id, titulo = detalle.titulo)
}
```

Si la pantalla tiene un ViewModel, este también puede leer los argumentos directamente a partir de su `SavedStateHandle`:

```kotlin
class DetalleViewModel(savedStateHandle: SavedStateHandle) : ViewModel() {
    private val detalle = savedStateHandle.toRoute<Detalle>()
    val id = detalle.id
}
```

:::warning[Pasa identificadores, no objetos]
Aunque sea tentador pasar un objeto completo a la siguiente pantalla, lo recomendable es pasar solo lo mínimo, normalmente su **identificador**, y que la pantalla de destino (o su ViewModel) obtenga el resto de datos desde el repositorio. Así los datos siempre están actualizados y la ruta es sencilla.
:::

## Navigation 3 (contenido adicional, no entra en examen)

En 2025 Google publicó **Navigation 3**, una nueva librería de navegación diseñada desde cero para Compose, en la que la pila de pantallas es una simple lista de rutas que controlamos nosotros. Navigation Compose, la que se explica en estos apuntes, sigue siendo totalmente válida y es la que utilizan la mayoría de proyectos y codelabs, pero conviene saber que existe la nueva librería. Más información en la [documentación de Navigation 3](https://developer.android.com/guide/navigation/navigation-3?hl=es-419).

:::tip[Contenido adicional (no entra en examen): qué cambia en Navigation 3]
Este apartado es solo para quien tenga curiosidad o quiera usar Navigation 3 en su proyecto. **No forma parte de la materia de examen.**

**La idea principal: la pila es nuestra**

En Navigation Compose, la pila de pantallas está "escondida" dentro del `NavController`: no la manipulamos directamente, sino que le pedimos al `NavController` que navegue (`navigate`) o que vuelva atrás (`popBackStack`), y él se encarga de actualizarla.

En Navigation 3 desaparece el `NavController`. La pila de pantallas (*back stack*) es simplemente **una lista de rutas que creamos y modificamos nosotros**, y la librería se limita a mostrar en pantalla la ruta que está al final de la lista. Es la misma filosofía que el resto de Compose: **la interfaz es una función del estado**, y aquí el estado es esa lista.

- Navegar a una pantalla → **añadir** una ruta a la lista: `backStack.add(Perfil)`.
- Volver atrás → **quitar** la última ruta de la lista: `backStack.removeLastOrNull()`.
- Cualquier otra operación (vaciar la pila, sustituir una pantalla, volver al inicio...) → usar las funciones normales de una lista de Kotlin.

**Equivalencias con lo visto en el tema**

| Navigation Compose (este tema) | Navigation 3 |
|---|---|
| Rutas con `@Serializable` | Rutas con `@Serializable` que además implementan la interfaz `NavKey` |
| `rememberNavController()` | `rememberNavBackStack(rutaInicial)`, que devuelve una lista de rutas |
| `NavHost` | `NavDisplay` |
| `startDestination = Inicio` | La ruta que pasamos al crear la pila |
| `composable<Ruta> { ... }` | `entry<Ruta> { ... }` dentro de un `entryProvider` |
| `navController.navigate(Perfil)` | `backStack.add(Perfil)` |
| `navController.popBackStack()` | `backStack.removeLastOrNull()` |
| `popUpTo`, `launchSingleTop`... | Operaciones normales de lista (`clear`, `removeAll`, `contains`...) |
| `backStackEntry.toRoute<Detalle>()` | La propia ruta llega como parámetro de `entry<Detalle> { ruta -> ... }` |

**Otros añadidos**

- **Recuperar argumentos es más directo**: como la pila contiene las propias rutas, en `entry<Detalle> { detalle -> ... }` recibimos directamente el objeto `Detalle` con sus propiedades. No hace falta `toRoute()`.
- **Gestión del botón "atrás" explícita**: `NavDisplay` recibe un parámetro `onBack` en el que decidimos qué hacer cuando el usuario pulsa "atrás" (normalmente, quitar la última ruta).
- **Varias pantallas a la vez (*scenes*)**: Navigation 3 permite mostrar varias rutas de la pila al mismo tiempo, por ejemplo una lista y su detalle uno al lado del otro en tablets o móviles plegables. Con Navigation Compose esto era bastante más complicado.
- **Decoradores de entradas**: permiten añadir comportamiento a cada pantalla de la pila, como conservar su estado o tener un ViewModel propio para cada entrada (con la librería `lifecycle-viewmodel-navigation3`).

**Dependencias**

Navigation 3 sigue usando `kotlinx.serialization` para las rutas, así que el plugin y la librería de serialización se configuran igual que al principio del tema. Solo cambian las librerías de navegación:

```toml title="libs.versions.toml"
[versions]
nav3Core = "1.0.0"

[libraries]
androidx-navigation3-runtime = { group = "androidx.navigation3", name = "navigation3-runtime", version.ref = "nav3Core" }
androidx-navigation3-ui = { group = "androidx.navigation3", name = "navigation3-ui", version.ref = "nav3Core" }
```

```kotlin title="app/build.gradle.kts"
dependencies {
    implementation(libs.androidx.navigation3.runtime)
    implementation(libs.androidx.navigation3.ui)
}
```

**Ejemplo sencillo**

El mismo ejemplo del tema (inicio, perfil y detalle con un argumento) hecho con Navigation 3:

```kotlin
import androidx.navigation3.runtime.NavKey
import androidx.navigation3.runtime.entryProvider
import androidx.navigation3.runtime.rememberNavBackStack
import androidx.navigation3.ui.NavDisplay
import kotlinx.serialization.Serializable

// 1. Rutas: igual que antes, pero implementando NavKey
@Serializable
data object Inicio : NavKey

@Serializable
data object Perfil : NavKey

@Serializable
data class Detalle(val id: Int) : NavKey

@Composable
fun MyApp() {
    // 2. La pila de pantallas: una lista que empieza con la ruta Inicio
    val backStack = rememberNavBackStack(Inicio)

    // 3. NavDisplay muestra la última ruta de la lista
    NavDisplay(
        backStack = backStack,
        // Qué hacer al pulsar "atrás": quitar la última pantalla
        onBack = { backStack.removeLastOrNull() },
        // Qué composable se muestra para cada ruta
        entryProvider = entryProvider {
            entry<Inicio> {
                PantallaInicio(
                    onIrAPerfil = { backStack.add(Perfil) },
                    onIrADetalle = { id -> backStack.add(Detalle(id)) }
                )
            }
            entry<Perfil> {
                PantallaPerfil(
                    onVolver = { backStack.removeLastOrNull() }
                )
            }
            // La ruta llega como parámetro, con sus argumentos
            entry<Detalle> { detalle ->
                PantallaDetalle(id = detalle.id)
            }
        }
    )
}
```

Las pantallas (`PantallaInicio`, `PantallaPerfil`, `PantallaDetalle`) no cambian en absoluto: siguen recibiendo lambdas para los eventos de navegación, tal y como se explicó en el apartado de [navegación usando lambdas](#navegación-entre-pantallas-usando-lambdas). Esa es una de las ventajas de no pasar el `navController` a las pantallas: podemos cambiar de librería de navegación sin tocarlas.

Por último, algo equivalente a `popUpTo<Inicio> { inclusive = true }` tras un login sería, simplemente, vaciar la lista y añadir la nueva pantalla:

```kotlin
backStack.clear()
backStack.add(Inicio)
```
