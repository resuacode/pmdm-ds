# Conexión a internet

## Corrutinas en Android

Las corrutinas en Android son la forma recomendada de escribir código asíncrono. Permiten ejecutar tareas largas, como una petición HTTP o una consulta a la base de datos, **sin bloquear el hilo principal**, que es el encargado de dibujar la interfaz y responder al usuario. Si lo bloqueamos, la app se congela y, pasados unos segundos, Android muestra el diálogo de "La aplicación no responde" (ANR).

Ya vimos los conceptos básicos en el apartado de [corrutinas en Kotlin](./1-sobre-kotlin/61-corrutinas.mdx). Recordemos que una función que puede pausar su ejecución sin bloquear el hilo se marca con la palabra clave `suspend`:

```kotlin
object Timer {
    suspend fun start(callback: (Int) -> Unit) {
        var count = 0
        while (true) {
            delay(1000)
            count++
            callback(count)
        }
    }
}
```

En este ejemplo, la función `start` es una suspend function que inicia un conteo y llama a un callback cada segundo con el valor actual del contador. La función `delay` suspende la corrutina durante un segundo sin bloquear el hilo.

Una función `suspend` solo puede llamarse desde una corrutina. En un programa de consola podemos crear una con `runBlocking`, que bloquea el hilo hasta que termina:

```kotlin
// Solo para demos de consola / Playground
fun main() {
    runBlocking {
        Timer.start { count ->
            println("Count: $count")
        }
    }
}
```

En una app Android, en cambio, el mismo código se lanzaría así desde un ViewModel:

```kotlin
// En un ViewModel de Android
class TimerViewModel : ViewModel() {
    fun start() {
        viewModelScope.launch {
            Timer.start { count -> /* actualizar StateFlow */ }
        }
    }
}
```

En el ejemplo de consola, `runBlocking` espera a la corrutina. En Android, el alcance del ViewModel cancela el trabajo cuando el ViewModel se destruye. 

En Android **nunca** usaremos `runBlocking`, sino los ámbitos de corrutinas (*coroutine scopes*) que nos proporciona Jetpack y que se cancelan automáticamente cuando dejan de ser necesarios:

- `viewModelScope`: dentro de un ViewModel. Es el que usaremos para las peticiones a internet y a la base de datos.
- `LaunchedEffect` y `rememberCoroutineScope()`: dentro de un composable.

![Corroutine Scope](https://developer.android.com/static/codelabs/basic-android-kotlin-compose-coroutines-android-studio/img/a3c314fb082a9626_960.png?hl=es-419)

:::tip[La palabra clave suspend]
La palabra clave suspend en Kotlin se utiliza para marcar una función que puede pausar su ejecución y reanudarla más tarde. Las funciones suspendidas se utilizan en las corrutinas para realizar operaciones asíncronas de forma eficiente.
:::

### LaunchedEffect para ejecutar tareas en segundo plano en Jetpack Compose

`LaunchedEffect` es un composable que lanza una corrutina cuando entra en la composición y la **cancela automáticamente** cuando sale de ella.

Por ejemplo, el siguiente código muestra un composable que muestra un contador que se actualiza cada segundo:

```kotlin
@Composable
fun Timer() {
    var count by remember { mutableIntStateOf(0) }

    LaunchedEffect(Unit) {
        while (true) {
            delay(1000)
            count++
        }
    }

    Text(text = "Count: $count")
}
```

En este ejemplo, el composable `Timer` muestra un contador que se actualiza cada segundo. `LaunchedEffect` inicia un bucle infinito que, gracias a `delay`, no bloquea el hilo. Cuando `Timer` deja de mostrarse (por ejemplo, al navegar a otra pantalla), la corrutina se cancela sola, por lo que no hace falta hacer nada para detenerla.

El parámetro de `LaunchedEffect` (en el ejemplo, `Unit`) es la **clave**: si cambia, la corrutina en curso se cancela y se lanza una nueva. Con `Unit` se ejecuta una sola vez. Si, por ejemplo, queremos volver a cargar datos cada vez que cambia un identificador, lo pasamos como clave:

```kotlin
LaunchedEffect(usuarioId) {
    // Se vuelve a ejecutar cada vez que cambia usuarioId
}
```

### rememberCoroutineScope para lanzar corrutinas desde eventos

`LaunchedEffect` sirve para tareas que se lanzan al mostrarse el composable. Pero si queremos lanzar una corrutina en respuesta a un **evento del usuario**, como pulsar un botón, no podemos usar `LaunchedEffect` dentro de un `onClick`, porque `onClick` no es un composable. Para eso se usa `rememberCoroutineScope()`, que devuelve un ámbito ligado al composable:

```kotlin
@Composable
fun Carrera() {
    var progreso by remember { mutableFloatStateOf(0f) }
    val scope = rememberCoroutineScope()

    Column {
        LinearProgressIndicator(progress = { progreso })
        Button(onClick = {
            scope.launch {
                progreso = 0f
                while (progreso < 1f) {
                    delay(100)
                    progreso += 0.05f
                }
            }
        }) {
            Text("Empezar")
        }
    }
}
```

Las corrutinas lanzadas con este `scope` también se cancelan automáticamente cuando el composable sale de la composición.

:::warning[Corrutinas en los composables o en el ViewModel]
`LaunchedEffect` y `rememberCoroutineScope` están pensados para lógica **de la interfaz** (animaciones, mostrar un snackbar, desplazar una lista...). Las operaciones que obtienen o guardan datos, como las peticiones a internet, deben lanzarse desde el **ViewModel** con `viewModelScope`, que sobrevive a los giros de pantalla. Si lanzáramos una petición desde un composable, se cancelaría y repetiría cada vez que se gira la pantalla.
:::

Un ejemplo de uso de corrutinas en Compose podemos encontrarlo en el siguiente Codelab, en el que se implementa una carrera ficticia entre dos jugadores:

[Codelab: Carrera de coches ficticia](https://developer.android.com/codelabs/basic-android-kotlin-compose-coroutines-android-studio?hl=es-419)

:::tip[LaunchedEffect]
Una de las principales ventajas del uso de `LaunchedEffect` es que se ejecuta en el ámbito del composable, lo que significa que se cancela automáticamente cuando el composable se elimina de la composición. Esto evita que queden tareas ejecutándose cuando ya no son necesarias.

Las corrutinas de `LaunchedEffect`, `rememberCoroutineScope` y `viewModelScope` se ejecutan por defecto en el hilo principal (`Dispatchers.Main`). Esto no es un problema mientras solo llamemos a funciones `suspend` (como `delay` o las de Retrofit y Room), ya que suspenden sin bloquear. Si necesitamos hacer un trabajo pesado que bloquee (leer un fichero, un cálculo largo...), lo envolveremos en `withContext(Dispatchers.IO)` o `withContext(Dispatchers.Default)`.
:::

Para conectarse a internet en una aplicación Android con Jetpack Compose, puedes utilizar las siguientes opciones (existen más opciones, pero estas son las más comunes):  

- **Retrofit**: Biblioteca de cliente HTTP para Android y Java que facilita la conexión a servicios web RESTful. Es la opción que usaremos en el curso.

- **Ktor Client**: Ktor es un framework de JetBrains, escrito en Kotlin, para crear clientes y servidores web. Su cliente HTTP es una alternativa a Retrofit muy usada en proyectos Kotlin Multiplatform.

- **Volley**: Volley es una biblioteca de red de Google, más antigua, que facilita la conexión a servicios web en Android. La verás en material antiguo, pero hoy en día apenas se usa en proyectos nuevos y no es la que usaremos en el curso.

## ¿Qué es Retrofit?

Retrofit es una biblioteca de cliente HTTP para Android y Java que facilita la conexión a servicios web RESTful. Retrofit te permite definir una interfaz de servicio web con anotaciones que describen las operaciones disponibles en el servicio, como las peticiones GET, POST, PUT y DELETE. Retrofit se encarga de convertir las respuestas del servidor en objetos Java/Kotlin y de gestionar la comunicación con el servidor de forma eficiente.

![Ejemplo de Petición http](https://developer.android.com/static/codelabs/basic-android-kotlin-compose-getting-data-internet/img/301162f0dca12fcf_960.png)
![Ejemplo de respuesta http](https://developer.android.com/static/codelabs/basic-android-kotlin-compose-getting-data-internet/img/7ced9b4ca9c65af3_960.png)

:::info[Tipos de peticiones habituales HTTP]
- **GET**: Se utiliza para obtener datos del servidor. Por ejemplo, puedes utilizar una petición GET para obtener una lista de usuarios de un servidor.
- **POST**: Se utiliza para enviar datos al servidor. Por ejemplo, puedes utilizar una petición POST para enviar un formulario con los datos de un nuevo usuario al servidor.
- **PUT**: Se utiliza para actualizar datos en el servidor. Por ejemplo, puedes utilizar una petición PUT para actualizar los datos de un usuario existente en el servidor.
- **DELETE**: Se utiliza para eliminar datos del servidor. Por ejemplo, puedes utilizar una petición DELETE para eliminar un usuario del servidor.

![Ejemplo de petición http](https://developer.android.com/static/codelabs/basic-android-kotlin-compose-getting-data-internet/img/5bbeef4ded3e84cf_960.png)
![Ejemplo de respuesta http](https://developer.android.com/static/codelabs/basic-android-kotlin-compose-getting-data-internet/img/83e8a6eb79249ebe_960.png)
:::

## Implementación de Retrofit en Jetpack Compose

Para implementar Retrofit en una aplicación Android con Jetpack Compose, puedes seguir los siguientes pasos:

1. **Definir la interfaz de servicio web**: Define una interfaz que contenga las operaciones disponibles en el servicio web y anótala con las anotaciones de Retrofit, como `@GET`, `@POST`, `@PUT` y `@DELETE`. Por ejemplo, puedes definir una interfaz `ApiService` que contenga métodos para obtener y enviar datos al servidor.

2. **Crear una instancia de Retrofit**: Crea una instancia de Retrofit utilizando `Retrofit.Builder` y configura la URL base del servicio web y el convertidor de JSON. Por ejemplo, puedes crear una instancia de Retrofit que se conecte a un servidor en `https://api.example.com/` y utilice el convertidor de JSON de Gson.

3. **Crear una instancia del servicio web**: Crea una instancia del servicio web a partir de la interfaz de servicio web y la instancia de Retrofit.

4. **Realizar peticiones HTTP**: Utiliza la instancia del servicio web para realizar peticiones HTTP al servidor y obtener los datos necesarios para tu aplicación. Por ejemplo, puedes utilizar el método `getUsers()` de la interfaz `ApiService` para obtener una lista de usuarios del servidor.

![Funcionamiento Retrofit](https://developer.android.com/static/codelabs/basic-android-kotlin-compose-getting-data-internet/img/26043df178401c6a_960.png)

## Ejemplo sencillo de implementación

A continuación, se muestra un resumen de todas las piezas de Retrofit juntas:

```kotlin
// Modelo de datos que representa cada usuario del JSON
data class User(val id: Int, val name: String)

// Define la interfaz de servicio web con las operaciones disponibles
interface ApiService {
    @GET("users")
    suspend fun getUsers(): List<User>
}

// Crea una instancia de Retrofit con la URL base y el convertidor de JSON
val retrofit = Retrofit.Builder()
    .baseUrl("https://api.example.com/")
    .addConverterFactory(GsonConverterFactory.create())
    .build()

// Crea una instancia del servicio web a partir de la interfaz y de Retrofit
val apiService = retrofit.create(ApiService::class.java)

// Realiza una petición HTTP (desde una corrutina, ya que getUsers es suspend)
val users = apiService.getUsers()
```

En este ejemplo, se define una interfaz `ApiService` con el método `getUsers()` que realiza una petición GET a `https://api.example.com/users` para obtener una lista de usuarios. Se crea una instancia de Retrofit con la URL base y el convertidor de JSON de Gson. A continuación, se crea una instancia del servicio web a partir de la interfaz `ApiService`. Por último, se utiliza para obtener la lista de usuarios. Como `getUsers()` es una función `suspend`, Retrofit se encarga de hacer la petición fuera del hilo principal.

Todo este código suele ordenarse y distribuirse en diferentes archivos y paquetes para mantener una estructura limpia y organizada. A continuación veremos cada uno de estos pasos en detalle.  

## Implementación de Retrofit en Android

### Permiso de Internet

Para conectarse a internet en una aplicación Android, debes añadir el permiso de internet al archivo `AndroidManifest.xml` de la aplicación, fuera de la etiqueta `<application>`:

```xml title="AndroidManifest.xml"
<manifest xmlns:android="http://schemas.android.com/apk/res/android">

    <uses-permission android:name="android.permission.INTERNET" />

    <application
        ...>
    </application>
</manifest>
```

Sin este permiso, la aplicación no podrá conectarse a internet y las peticiones fallarán con una excepción de seguridad.

:::warning[Solo HTTPS]
Por seguridad, a partir de Android 9 las apps solo pueden conectarse por defecto a direcciones **HTTPS**. Si la API que queremos usar solo funciona con HTTP (por ejemplo, un servidor local de pruebas), hay que permitirlo explícitamente con `android:usesCleartextTraffic="true"` en la etiqueta `<application>`, algo que nunca debería hacerse en una app publicada.
:::

### Importar las dependencias de Retrofit

#### Paso a paso

1. Abre `gradle/libs.versions.toml` (o el `build.gradle.kts` del módulo `app` si aún no usas catalog).
2. Añade Retrofit y el convertidor que vayas a usar (Scalars para las primeras pruebas, Gson o kotlinx.serialization para JSON), como se muestra a continuación.
3. Pulsa **Sync Now**.
4. Añade el permiso `INTERNET` en el manifest (apartado anterior).
5. Si Sync falla, consulta la [guía de problemas Gradle](./12-gradle-troubleshooting.mdx).

Para utilizar Retrofit, primero debemos añadir sus dependencias. En los proyectos actuales de Android Studio, las versiones se centralizan en el archivo `gradle/libs.versions.toml`:

```toml title="libs.versions.toml"
[versions]
retrofit = "3.0.0"

[libraries]
retrofit = { group = "com.squareup.retrofit2", name = "retrofit", version.ref = "retrofit" }
retrofit-converter-gson = { group = "com.squareup.retrofit2", name = "converter-gson", version.ref = "retrofit" }
retrofit-converter-scalars = { group = "com.squareup.retrofit2", name = "converter-scalars", version.ref = "retrofit" }
```

```kotlin title="app/build.gradle.kts"
dependencies {
    // Retrofit
    implementation(libs.retrofit)
    // Convertidor de JSON a objetos con Gson
    implementation(libs.retrofit.converter.gson)
    // Convertidor de la respuesta a String (opcional)
    implementation(libs.retrofit.converter.scalars)
}
```

Si no usamos el catálogo de versiones, se pueden escribir directamente:

```kotlin title="app/build.gradle.kts"
dependencies {
    implementation("com.squareup.retrofit2:retrofit:3.0.0")
    implementation("com.squareup.retrofit2:converter-gson:3.0.0")
    implementation("com.squareup.retrofit2:converter-scalars:3.0.0")
}
```

La primera dependencia es Retrofit. Las otras dos son **convertidores**: el de Gson transforma el JSON de la respuesta en objetos de Kotlin (e incluye ya la librería Gson), y el de escalares (*scalars*) devuelve la respuesta como un `String` sin transformar, lo cual es útil para hacer las primeras pruebas.

:::warning[Si Sync falla con Retrofit]
- “Could not resolve”: red del aula o versión mal escrita → [guía Gradle](./12-gradle-troubleshooting.mdx).
- Asegúrate de tener `google()` y `mavenCentral()` en los repositorios.
:::

### Definir la interfaz de servicio web

A continuación, debes definir una interfaz de servicio web que contenga las operaciones disponibles en el servicio. Cada función se anota con el tipo de petición (`@GET`, `@POST`, `@PUT`, `@DELETE`) y la ruta relativa a la URL base:

```kotlin
import retrofit2.http.*

interface ApiService {
    @GET("users")
    suspend fun getUsers(): List<User>

    // Parámetro en la ruta: users/5
    @GET("users/{id}")
    suspend fun getUser(@Path("id") id: Int): User

    // Parámetro en la query: users?page=2
    @GET("users")
    suspend fun getUsersPage(@Query("page") page: Int): List<User>

    // Envía un objeto en el cuerpo de la petición como JSON
    @POST("users")
    suspend fun createUser(@Body user: User): User
}
```

En este ejemplo, la interfaz `ApiService` contiene varios métodos que realizan peticiones al servidor. Las anotaciones `@Path`, `@Query` y `@Body` indican cómo se incluye cada parámetro en la petición.

:::tip[Ubicación de la interfaz de servicio web en el proyecto]
La interfaz de servicio web suele ubicarse en un paquete `data`, `network` o `remote` del proyecto para mantener una estructura limpia y organizada.
:::

### Crear una instancia de Retrofit

Una vez que hayas definido la interfaz de servicio web, debes crear una instancia de Retrofit utilizando `Retrofit.Builder`, configurando la URL base del servicio web y el convertidor de JSON:

```kotlin
private const val BASE_URL = "https://api.example.com/"

val retrofit: Retrofit = Retrofit.Builder()
    .baseUrl(BASE_URL)
    .addConverterFactory(GsonConverterFactory.create())
    .build()
```

:::warning[La URL base debe terminar en `/`]
Retrofit lanza una excepción si la URL base no termina con una barra. Además, las rutas de las anotaciones (`@GET("users")`) no deben empezar por `/`, ya que en ese caso se ignoraría la parte de la ruta incluida en la URL base.
:::

:::tip[Ubicación de la instancia de Retrofit en el proyecto]
La instancia de Retrofit suele ubicarse en un archivo Kotlin en el paquete de datos, network o servicios del proyecto para mantener una estructura limpia y organizada.
:::

:::tip[Convertidores de Retrofit]
Retrofit utiliza convertidores para transformar las respuestas del servidor en objetos Java/Kotlin y viceversa. 
Existen convertidores para Gson, Moshi, Jackson, kotlinx.serialization y Scalars, entre otros. Cada uno tiene sus propias ventajas, por lo que debes elegir el que mejor se adapte a tus necesidades.

Por ejemplo, para recibir la respuesta como un simple `String` usaríamos Scalars (y la función del servicio devolvería `String`):

```kotlin
.addConverterFactory(ScalarsConverterFactory.create())
```

En el apartado [Conversión JSON a objetos](./8-trabajando-con-json.mdx) veremos cómo usar `kotlinx.serialization`, que es la alternativa recomendada en proyectos Kotlin.
:::

### Crear una instancia del servicio web

Una vez que hayas creado una instancia de Retrofit, debes crear una instancia del servicio web a partir de la interfaz con el método `create()`:

```kotlin
val apiService: ApiService = retrofit.create(ApiService::class.java)
```

Retrofit genera automáticamente una clase que implementa la interfaz `ApiService` y que realiza las peticiones HTTP.

Crear la instancia de Retrofit es costoso, por lo que solo debería existir **una** en toda la aplicación. Podríamos guardarla en un `object` (un singleton) y acceder a ella desde cualquier parte, pero los singletons representan estados globales en la aplicación y hacen que el código sea difícil de probar, ya que no se pueden sustituir por versiones de prueba.

En su lugar, es preferible utilizar **inyección de dependencias**: cada clase recibe en su constructor los objetos que necesita, en lugar de crearlos o buscarlos ella misma. Vamos a acostumbrarnos a gestionar las dependencias de esta forma, ya que es una buena práctica de programación.

Para esto separaremos claramente la capa de datos de la de UI a través de un repositorio o *Repository*, que será el encargado de gestionar las peticiones al servidor y devolver los datos a la capa de UI.

![Separación de la Data Layer](https://developer.android.com/static/codelabs/basic-android-kotlin-compose-add-repository/img/dbf927072d3070f0_960.png)


### Creación de un repositorio

Crearemos un nuevo paquete llamado `data` y en él una interfaz `UsersRepository` con los métodos para obtener los datos, junto con una clase que la implementa usando el servicio de Retrofit.

Definir el repositorio como una interfaz permite, por ejemplo, crear una versión falsa con datos de prueba para los tests o para las *previews*, sin tener que cambiar el resto de la app.

```kotlin
interface UsersRepository {
    suspend fun getUsers(): List<User>
}

class NetworkUsersRepository(
    private val apiService: ApiService
) : UsersRepository {
    override suspend fun getUsers(): List<User> = apiService.getUsers()
}
```

En este ejemplo, la interfaz `UsersRepository` define un método `getUsers()` que obtiene una lista de usuarios. La clase `NetworkUsersRepository` implementa la interfaz y recibe el servicio de Retrofit en su constructor, en lugar de crearlo ella misma: eso es la inyección de dependencias.

:::tip[Ubicación del repositorio en el proyecto]
El repositorio suele ubicarse en el paquete `data` del proyecto para mantener una estructura limpia y organizada.
:::

### Inyección de dependencias

La inyección de dependencias no es más que un patrón de diseño que se utiliza para desacoplar las dependencias de los objetos y facilitar su gestión.

Para implementar la inyección de dependencias en la aplicación, puedes utilizar una biblioteca como Hilt (la recomendada por Google), Koin o Dagger. Sin embargo, en este caso vamos a utilizar la inyección de dependencias **manual**, que nos ayuda a entender qué hacen estas librerías por debajo.

Para ello, vamos a crear un **contenedor de dependencias**: una clase que crea una única vez los objetos de la capa de datos (Retrofit, el servicio y el repositorio) y los proporciona a quien los necesite. Como en el resto de casos, lo definimos a partir de una interfaz:

```kotlin title="data/AppContainer.kt"
interface AppContainer {
    val usersRepository: UsersRepository
}

class DefaultAppContainer : AppContainer {
    private val baseUrl = "https://api.example.com/"

    private val retrofit: Retrofit = Retrofit.Builder()
        .baseUrl(baseUrl)
        .addConverterFactory(GsonConverterFactory.create())
        .build()

    private val retrofitService: ApiService by lazy {
        retrofit.create(ApiService::class.java)
    }

    override val usersRepository: UsersRepository by lazy {
        NetworkUsersRepository(retrofitService)
    }
}
```

En este ejemplo, la interfaz `AppContainer` define una propiedad `usersRepository`, y la clase `DefaultAppContainer` la implementa creando Retrofit, el servicio y el repositorio. Gracias a `by lazy`, cada objeto se crea la primera vez que se necesita y después se reutiliza.

:::tip[Ubicación del contenedor de dependencias en el proyecto]
El contenedor de dependencias suele ubicarse en el paquete `data` del proyecto.
:::

### Adjuntar el contenedor de dependencias a la aplicación

El contenedor debe existir mientras exista la aplicación y debe haber uno solo. El lugar adecuado para crearlo es la clase `Application`, de la que Android crea una única instancia al arrancar la app, antes que cualquier actividad:

```kotlin title="MyApplication.kt"
class MyApplication : Application() {
    lateinit var container: AppContainer

    override fun onCreate() {
        super.onCreate()
        container = DefaultAppContainer()
    }
}
```

En este ejemplo, la clase `MyApplication` extiende de `Application` y crea el contenedor de dependencias en el método `onCreate()`.

:::tip[Ubicación de la clase Application en el proyecto]
La clase `Application` suele ubicarse en el paquete raíz de la aplicación, junto a la `MainActivity`.
:::

Debemos también actualizar el archivo `AndroidManifest.xml` para que Android utilice nuestra clase `MyApplication`, añadiendo el atributo `android:name` a la etiqueta `<application>` (el resto de atributos se quedan como estaban):

```xml title="AndroidManifest.xml"
<application
    android:name=".MyApplication"
    android:allowBackup="true"
    android:icon="@mipmap/ic_launcher"
    android:label="@string/app_name"
    android:roundIcon="@mipmap/ic_launcher_round"
    android:supportsRtl="true"
    android:theme="@style/Theme.MyApp">
```

:::warning[Si la app se cierra al arrancar]
Si olvidamos añadir `android:name=".MyApplication"` al manifiesto, Android usará la clase `Application` por defecto y, al intentar convertirla en `MyApplication` para acceder al contenedor, la app se cerrará con una `ClassCastException`.
:::

### Utilizar el repositorio en la capa de UI (En el ViewModel)

El ViewModel recibe el repositorio como parámetro de su constructor. Así no necesita saber de dónde vienen los datos, y en los tests podemos pasarle un repositorio falso.

Para representar los posibles estados de la pantalla (cargando, datos obtenidos o error) usamos una interfaz sellada, como vimos en el apartado de [sealed classes](./1-sobre-kotlin/26-sealed-classes.mdx):

```kotlin title="ui/UsersViewModel.kt"
sealed interface UsersUiState {
    data object Loading : UsersUiState
    data class Success(val users: List<User>) : UsersUiState
    data class Error(val message: String) : UsersUiState
}

class UsersViewModel(
    private val usersRepository: UsersRepository
) : ViewModel() {

    private val _uiState = MutableStateFlow<UsersUiState>(UsersUiState.Loading)
    val uiState: StateFlow<UsersUiState> = _uiState.asStateFlow()

    init {
        getUsers()
    }

    fun getUsers() {
        viewModelScope.launch {
            _uiState.value = UsersUiState.Loading
            _uiState.value = try {
                UsersUiState.Success(usersRepository.getUsers())
            } catch (e: IOException) {
                UsersUiState.Error("Error de conexión")
            } catch (e: HttpException) {
                UsersUiState.Error("Error del servidor: ${e.code()}")
            }
        }
    }

    companion object {
        val Factory: ViewModelProvider.Factory = viewModelFactory {
            initializer {
                val application = this[APPLICATION_KEY] as MyApplication
                UsersViewModel(application.container.usersRepository)
            }
        }
    }
}
```

En este ejemplo, la clase `UsersViewModel` recibe el repositorio en su constructor y, al crearse, lanza la petición en `viewModelScope`. Si la petición va bien, el estado pasa a `Success` con la lista de usuarios; si falla por un problema de red (`IOException`) o por una respuesta de error del servidor (`HttpException`), pasa a `Error`.

:::warning[Captura siempre los errores de red]
Una petición a internet puede fallar en cualquier momento: el dispositivo puede no tener conexión, el servidor puede estar caído o devolver un error. Si no capturamos la excepción, **la app se cerrará**.
:::

Como el ViewModel ahora tiene un parámetro en su constructor, Android no sabe cómo crearlo por sí solo. Para ello definimos una **factory** (una implementación del patrón Factoría, encargado de crear objetos) en el `companion object` del ViewModel:

- `viewModelFactory { initializer { ... } }` crea la factory. Dentro de `initializer` escribimos cómo construir el ViewModel.
- `this[APPLICATION_KEY]` nos da la instancia de la aplicación, que convertimos a `MyApplication` para acceder a su contenedor y obtener el repositorio.

:::tip[Ubicación del ViewModel en el proyecto]
El ViewModel suele ubicarse en el paquete `ui` del proyecto, junto a la pantalla que lo usa.
:::

:::info[La palabra reservada companion en Kotlin]
La palabra reservada `companion` en Kotlin se utiliza para definir miembros que pertenecen a la clase en lugar de a cada instancia, de forma similar a los miembros `static` de Java.
En este ejemplo, se utiliza para definir la `Factory` del ViewModel, a la que accedemos como `UsersViewModel.Factory`.
:::


### Utilizar el ViewModel en la capa de UI (En el Composable)

En el composable obtenemos el ViewModel con la función `viewModel()`, pasándole la factory, y recogemos su estado con `collectAsStateWithLifecycle()`. Después, con un `when`, mostramos una cosa u otra según el estado:

```kotlin title="ui/UsersScreen.kt"
@Composable
fun UsersScreen(
    modifier: Modifier = Modifier,
    viewModel: UsersViewModel = viewModel(factory = UsersViewModel.Factory)
) {
    val uiState by viewModel.uiState.collectAsStateWithLifecycle()

    when (val state = uiState) {
        UsersUiState.Loading -> CircularProgressIndicator(modifier = modifier)
        is UsersUiState.Success -> LazyColumn(modifier = modifier) {
            items(state.users, key = { it.id }) { user ->
                Text(user.name)
            }
        }
        is UsersUiState.Error -> Column(modifier = modifier) {
            Text(state.message)
            Button(onClick = viewModel::getUsers) { Text("Reintentar") }
        }
    }
}
```

En este ejemplo, el composable `UsersScreen` muestra un indicador de carga mientras se obtienen los datos, la lista de usuarios cuando llegan o un mensaje de error con un botón para reintentar.

:::tip[Ubicación del Composable en el proyecto]
El Composable suele ubicarse en el paquete `ui` del proyecto para mantener una estructura limpia y organizada.
:::
